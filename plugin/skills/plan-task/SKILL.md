# Plan Task

Orchestrate the analysis → design → planning pipeline by delegating to specialized agents, then drive execution with validation gates.

**Default branch resolution:** read `repo.default_branch` from `.gvt-agent.json`; if absent, fall back to `git symbolic-ref --short refs/remotes/origin/HEAD`. Below, `<default-branch>` refers to this value.

**See also:** `${CLAUDE_PLUGIN_ROOT}/docs/development-principles.md` for the philosophy behind the pipeline. Sub-docs in this skill: [`multi-session.md`](multi-session.md), [`approval-and-audit.md`](approval-and-audit.md).

## Pipeline

### Phase 0: Locate prior context

Before dispatching the analyst, check whether this task extends prior work. The project may have its own initiative-tracking convention — consult `CLAUDE.md` for any such convention. Common signals to look for:

- The task description references a previously-shipped feature, PR, or pattern by name
- The task is a follow-up the user mentioned in a prior session or retro
- Existing tracking files (initiative docs, roadmaps, ADRs) list the work as pending

If related prior context exists, default to **extending it** rather than starting fresh. Reuse existing requirements docs if the new work logically belongs in their scope.

If no related context exists, proceed normally.

### Phase 1: Analysis

Dispatch a recon agent with the task description to explore the problem space, identify requirements, and document constraints. **Prefer the project's domain explorer** when the task is domain-specific: a domain task (e.g. a Construct 3 event-sheet migration) needs the domain's MCP tools, which the generic analyst lacks — check `CLAUDE.md` for any agent-dispatch guidance naming a better-fit recon agent (e.g. `<domain-plugin>:<explorer>`) and dispatch that instead. **Fall back to `gvt-dev:analyst`** for general tasks, or when `CLAUDE.md` names no domain explorer.

**Input:** the user's task description plus any relevant prior context (initiative docs, prior work).

**Output:** a requirements document. Present it to the user.

**For bug tickets, confirm the reported symptom is observable before moving to design.** Reproduce it, or trace the *read/render* path end-to-end (who actually observes the suspect value), not just the *write* path. A defect can exist in the code yet never surface — a self-healing re-render, a `trigger-once` re-init, or every reader re-deriving the value from a correct source can mask it. If no reader observes the bad value, reclassify the task as tech-debt/cleanup (`chore`/`refactor`) rather than a fix, and say so explicitly to the user. **When a candidate looks like a bug *because it diverges from a reference fix or established pattern*, verify the reference itself targeted an observable reader on the path in question** — don't infer observability transitively from "the pattern patches this." A reference fix's own defensive (non-observable) patch can make a harmless sibling look like a real gap. (This is distinct from the "re-trace on didn't work" check during execution, which verifies a *fix* worked — this verifies the *bug is real* up front.)

**For feature tickets, confirm the capability isn't already shipped before designing.** Grep the codebase for the named capability (function, flag, tool, doc) and read the issue *body*, not just its title/labels — a long-lived "feat:" issue is often a tracking issue whose core work already landed, carrying only residual follow-up checkboxes. If it's shipped, scope the plan to the open checkboxes and **verify each is still representable** (a follow-up can be moot — e.g. it targets a state that can't occur). If the whole thing is already shipped, say so explicitly and propose closing rather than planning. **For a dependency-bump issue, verify the bump is real before treating it as dependency work:** a `^`/`~` range may already resolve to the target version in the lockfile, so a "bump to vX" is often *not* real dependency work — the new APIs are already installed and callable, and the substance is *adoption*, not the bump. Read the lockfile entry or installed package version; if the existing range already resolves to the target, scope the plan as a floor bump + **adoption** (a one-line `package.json` floor change + the actual adoption refactor/coverage), not a dependency upgrade. A purely-inherited upstream change — rendering or behavior delegated transparently to the dependency, no local code change — may need **only** new test/fixture coverage to lock it in. (Surfaced as construct3-chef #101: "update c3source to 1.7.0" read as a version bump, but `@genvidtech/c3source@^1.6.0` had already resolved to 1.7.0 in the lockfile — the real work was a literal→handle adoption refactor + fixture coverage, not the bump.) **Conversely, a caret that merely *permits* the target does not mean it is installed:** the discriminator is the lockfile's *current pin*, not what the range allows — distinguish *permits* from *currently resolves to*. If the lockfile still pins the older version, the bump is **real work** (a `package.json` floor change + an `npm install` lockfile refresh), the new APIs aren't callable until that refresh lands, and adoption can't even be attempted before it. (Surfaced as c3-domain-manager #25: `@genvidtech/c3source: "^1.7.0"` permitted 1.8.0 but `package-lock.json` still pinned 1.7.0, so the 1.8.0 APIs were not installed — the bump was real, not a no-op.) **For a vendored or binary dependency** (a checked-in addon/plugin blob, a copied library, an LFS asset) there is no lockfile — the equivalent checks are (a) inspect the **vendored artifact's own embedded version** (e.g. unzip its manifest) against the target, and (b) verify the issue body's **reconciliation premise** (CI pins, docs, surrounding config) against current state, since a prior PR may have already done the surrounding migration and left only the blob swap — or nothing. (Surfaced on a burbank task bumping two vendored `.c3addon` blobs: there was no range to read, and the staleness that mattered was the issue's premise that a CI + docs scope migration was still pending when a prior PR had already shipped it, leaving just the blob swap.)

**A prescribed mechanism raises three independent questions, and the ticket's type doesn't gate which apply — a bug ticket prescribes a mechanism as readily as a feature one.** **Is it current?** Also check whether a prescribed mechanism has been superseded: if the issue specifies an implementation mechanism (specific functions, a named structure, a convention), re-verify it against live code — a later change may have shipped a different mechanism, leaving the issue's prescription dead and never adopted (see `development-principles.md` principle #8, stale-mechanism corollary). If so, surface "mechanism superseded by \<PR\>" and plan to reconcile the issue body in the same PR rather than silently adopting the stale prescription. **Is it sufficient?** A mechanism can be live, coherent, and un-superseded and still be structurally unable to satisfy the issue's own acceptance criteria — insufficiency is a distinct failure mode from supersession, and the supersession check above returns clean on an insufficient mechanism. When the issue states both a mechanism and the criteria it must meet, check the mechanism against those criteria, not only against the code. **Was it ever the best option?** A full proposal prescribes *a* mechanism, not necessarily the best one — on this path the designer, the phase that weighs alternatives, does not run, and an absent open-questions section is not evidence of a settled design. Name the axes an author had no reason to weigh — platform portability, dependency footprint, cost on a hot path, hermeticity — and route a live fork to `AskUserQuestion`, recommended option first, with the trade-off measured rather than asserted (the measured-claim re-derivation discipline above applies here too), citing `gvt-dev:build-probe`. (Symmetric with the bug-symptom-observable gate above — both verify the work is *real and unbuilt* before design, and this gate adds whether it is worth building *this way*. An upstream `plan-next-issue` may already flag a candidate as possibly-shipped; this is the planning-time re-check.)

**The reads that the feature-already-shipped gate above prescribes — the lockfile entry, the installed package version, the unzipped vendored manifest — settle *whether* a version is installed, and that's all they settle: every one of those is a version fact.** The sufficiency question above, for a dependency-bump or dependency-consuming mechanism, usually turns on something a version number can't answer — the dependency's *behavior* and its *call ordering* — so a mechanism that passes the version check can still fail the sufficiency check.

**When the prescription is "filter / short-circuit / early-return inside callback X," don't stop at the type signature — read the dependency's shipped implementation, its published `dist`, and confirm what the caller does *before* invoking X.** If the side effect you're guarding against has already happened by the time X runs, the call ordering puts the hook in the wrong place no matter how correct callback X's own logic is; types and docstrings state facts (a callback exists, its shape), not consequences (when it runs relative to the dependency's own internal steps) — and a locally-documented fact about the dependency, inherited from a comment or a prior session, is not sufficient evidence on its own.

**Before adopting any issue's prescribed content as fact, verify it against the artifact it modifies.** An issue proposing concrete replacement wording, a JSON/config shape, a snippet, or a schema can be wrong about the current state of the file it targets — and the reverse also happens, where the artifact is the one that's wrong. Read the target and diff the proposal's claims against it; don't assume either side is authoritative. Name the source that settles the conflict — an external spec, git history, or the artifact's own provenance — and surface it at the checkpoint as an explicit fork when no such source exists. See `development-principles.md` principle #13.

**When a task assigns work in a repository other than the one being planned in — a git submodule, a vendored dependency, an upstream fixture, or a sibling repo in the same org — read that repository's own contribution rules before planning work into it.** Its `README.md`, `CONTRIBUTING.md`, and `docs/decisions/` are where authoring constraints, required review or release steps, and any manual checkpoint live; neither the planning repo's code nor its own `CLAUDE.md` can reveal them. The constraint is usually on *method*, not *permission* — the change is allowed, but the route is restricted (e.g. a repo that requires an editor round-trip and forbids hand-authored project JSON), so a check phrased "may we change this repo?" passes and misses it. A satisfiable protocol is not a blocker: prefer keeping the planned mechanism and adding the step the protocol asks for, over abandoning the mechanism outright. Surface what you find at the checkpoint as an explicit fork — satisfy the protocol, choose a different mechanism, or hand the step to a human — and carry a human step into the plan as a task rather than a risk (`planner.md` now assigns these `— **human**`). Where the preceding paragraph asks whether a proposal's claims about an artifact are *correct*, this one asks whether you are *permitted to author* that artifact the way you intend — both fail late, during execution.

**A measured claim inherited from an issue is not covered by the artifact check above — re-derive it by running something.** *"Before adopting any issue's prescribed content as fact, verify it against the artifact it modifies"* reaches replacement wording, a config shape, a snippet, a schema — everything with a file to open. A benchmark, a platform matrix, a collision rate, or a timing figure has none; when such a figure is the stated justification for the mechanism being planned, or would be transcribed into an ADR, a docstring, or a CHANGELOG entry, re-measure it with `gvt-dev:build-probe` before the requirements checkpoint. Structural precision is not evidence of empirical precision. Correct a figure that fails to reproduce in the issue body, and never let the original reach shipped text.

**Checkpoint:** "Here are the requirements. Any additions or corrections?"

Wait for user feedback. Iterate if needed.

### Phase 2: Design

Dispatch the **`gvt-dev:designer`** agent with the approved requirements document.

**Input:** the requirements document plus any user feedback from Phase 1.

**Output:** a design document with options, friction audit, and test criteria.

**Checkpoint:** "Here's the proposed design. Which option do you prefer? Any concerns?"

**If the design concludes the work is really more than one issue, file the split issues before leaving this phase.** A designer's friction audit legitimately reaches "this is two issues, not one" — a natural seam (a read-only half and a mutating half), or a footprint past the single-session threshold. That verdict is a *tracker* change, not just a plan structure, and it must land here because **Phase 4's target-issue chain resolves only issues that already exist**: the `#N` in the task description now points at the wrong (parent) issue, and the issue-less fallback would silently absorb the case, writing criteria to `docs/acceptance/<slug>.md` while the real target has no criteria at all. So: confirm the proposed split with the user, **file each new issue** (linking them to the parent — as native sub-issues where the tracker supports it), record the split rationale as a comment on the original, and keep the original open as the *analysis of record* rather than closing it. Then re-enter Phase 3 planning the **first** split issue, and treat the rest as a queue the way `plan-next-issue` handles sequential runs. Filing is best-effort per `${CLAUDE_PLUGIN_ROOT}/docs/development-principles.md` principle #9 — if a create is blocked, surface the fully drafted bodies and stop rather than planning against an issue number that doesn't exist.

Wait for user feedback. Iterate if needed.

### Phase 3: Planning

Dispatch the **`gvt-dev:planner`** agent with the approved design document.

**Input:** the design document plus the user's chosen option and any feedback from Phase 2. **Pass the designer's `## Test Criteria` table through verbatim — do not summarize or paraphrase it.** Phase 4's pre-committed `## Acceptance Criteria` checklist is seeded directly from that table, so a summarized hand-off silently breaks the seeding: the planner, having nothing to transcribe, reconstructs its own criteria and its own numbering, and the resulting checklist looks complete while tracing to nothing. Summarizing the *rest* of the design is fine and often useful — the table specifically is a load-bearing artifact, not context. (Symptom to watch for: the planner's output says its acceptance criteria were "derived from the design prose" or "reconstructed" rather than transcribed. That is the planner correctly reporting that this hand-off dropped the table — treat it as a defect in the dispatch, not as a note to pass along.)

**"Verbatim" governs the row's *wording*, not its *truth* — correct a row whose premise has decayed, and say that you did.** A criterion can carry a concrete claim about the repo (a version string, a count, an enumerated set, a `file:line`), and the tree keeps moving between Phase 2 and Phase 3 — sometimes because of a PR this very session merged. Transcribing such a row unchanged writes a false assertion into the issue body, where two independent critics will grade against it. So before handing the table over, re-derive each row's concrete claims against the live tree, exactly as [`approval-and-audit.md`](approval-and-audit.md)'s premise cross-check requires of claims inherited from an issue — **the designer's own table is not exempt just because the plan authored it.** Where a claim has decayed, correct the row, state the correction and its evidence, and flag it to the planner as corrected. A corrected row still counts as **transcribed**, not reconstructed: the prohibition is on re-deriving criteria from the design prose and inventing a fresh numbering, not on keeping a row true. Watch for the case where the correction *inverts* what the row asks for rather than merely updating a number — a "leave X alone" row can silently become the load-bearing instruction. Do **not** quietly fix it and move on; an unrecorded correction is indistinguishable from a transcription error at review time.

**A behavioural claim has no value to re-derive, so this cross-check reaches it a different way.** Every claim named above — a version string, a count, an enumerated set, a `file:line` — is a concrete *value*, re-derivable by re-running the thing the row measures. A behavioural claim instead asserts what a **named subject** — a function, tool, handler, command, flag, or a **governing document** such as an ADR, a documented convention, or a `CLAUDE.md` rule — produces, emits, returns, rejects, **permits**, or **forbids**; there's nothing to re-run, so it's settled by reading the named subject itself, the general rule `designer.md`'s step 9, "Verify what you name before emitting," already owns. This is the transcription-scoped instance of that rule: the table here is one this phase is copying, not authoring, so a row citing a governing document is settled the same way a row naming a function is — **by opening the cited rule itself, not only the artifact the row's change edits** — a repo's own summary of the rule, or the artifact's compliance with it, is not a substitute for the rule's own text. **A row carrying no number is not exempt from this cross-check.** Re-running every baseline in the table is what "re-derive each row's concrete claims against the live tree" operationalizes to for a value-bearing row — a numberless row can look exempt for exactly that reason, but a behavioural row still owes the named-subject read; it simply has no baseline to re-run. **A row can also be born wrong rather than decayed.** The paragraph above is framed entirely around drift — "the tree keeps moving," "a PR this very session merged" — which structurally skips a claim that was never true when written. `plugin/agents/planner.md` already draws this line for its own corrections: *"a decayed row was right once, a mismarked row never was."* Cite that distinction rather than re-authoring it, and record which one applies when you correct a row.

**A row's baseline and its positive control are claims of the same rank as its expected value, and neither is settled by reading.** The paragraph above already states the baseline half — *"Re-running every baseline in the table is what 're-derive each row's concrete claims against the live tree' operationalizes to for a value-bearing row"* — which is a rule, not an aside about numberless rows: re-derivation means running the row's own command over the corpus the row names and comparing, mirroring the authoring-side obligation `designer.md` owns (*"Measure the baseline by running the row's own command against the pre-change tree — never assert one from reading the file"*). The **positive control** is the half with no statement in this skill at all. It is itself a claim about a corpus — "this pattern has exactly one hit in `<file>` today" — and it reads as justification for the row rather than as part of it, which is precisely why it goes unchecked: a control naming the wrong file, or a count taken over a corpus the row does not assert over, still reads as rigor. Re-run it too, over the corpus it names, and apply `designer.md`'s corpus rule (*"A baseline measured over a narrower corpus than the row asserts over is defective even though the measurement itself was correct"*) to both figures. What the re-run is *for* is the tell `planner.md` owns — *"if the baseline already satisfies the pass condition the row is vacuous"* — a row that grades green on an untouched checkout cannot detect this change's work and is a false green at both critics. Correct such a row and record the correction exactly as the paragraph above requires.

**Every integrity rule above hangs off the same moment — "before handing the table over" — and a row you authored yourself, mid-run, never passes through that moment.** A Phase-2 scope change surfaced only here, or a compressed shortcut path where the designer never ran, can put a criterion into the table that no transcription ever touched — it wasn't decayed, corrected, or cross-checked, because none of those rules trigger on a row with no prior draft to check against. **The binding rule is that a criterion is subject to the same obligations regardless of who authored it or when** — a row you write at the checkpoint owes exactly what a transcribed row owes, just discharged differently because there's no earlier draft to compare it to. Split by what the obligation needs: a **statically measurable** claim — a grep, a count, a file read against the current tree — is **run before the row is pledged, never asserted**, the same as any other baseline above. A claim resting on **pre-change tree state**, which no longer exists once execution has begun, can't be measured at the checkpoint at all — mark it **owed**, naming both an **owner** and a **time** at which it will be measured, rather than writing a number you cannot back. (Don't invent a marker token for this — `[point-in-time]` and `[not-yet-due]` tell the *graders* to treat a row differently, and an owed baseline is discharged before the pledge is written, so no grader ever sees it; minting a third token here would be grader-side vocabulary no issue asked for.) And a scope change large enough to need a genuinely **new** criterion — not a correction to an existing one — has outgrown the checkpoint: it re-enters design rather than being hand-authored here.

**Output:** an implementation plan with ordered tasks, domain assignments (see `CLAUDE.md` for the project's implementer-agent inventory), and risks.

**Checkpoint:** "Here's the implementation plan. Ready to proceed?"

Wait for explicit approval before saving. This is **plan approval**: it authorizes Phase 4 below — saving `plan.md`, creating the branch, writing the acceptance-criteria checklist, the prep commit — and stops there. The checkpoint wording above ("Ready to proceed?") is easily heard as "shall I implement it?", but the whole of Phase 4 sits between this approval and `## Execution (Post-Approval)`, which requires its own separate, explicit **execution approval** before the first implementer dispatch. See [`approval-and-audit.md`](approval-and-audit.md) for the self-audit checklist to run before presenting.

### Phase 4: Save and Branch

1. Save the plan to the repo root as `plan.md` (or to the project's planning location if `CLAUDE.md` specifies one). **If a `plan.md` already exists, classify it before overwriting** — a gitignored plan lingers on disk after its branch merges, so an existing file may describe earlier, *unrelated* work, and a gitignored plan's overwrite is unrecoverable (local-only, no git history to fall back on). Apply the same **already-shipped / spent / unshipped-pending** classification the *continuation* shortcut spells out below: overwrite freely when it's shipped **or spent** (its tasks are already committed somewhere — merged to `origin`, *or* on its own this-session branch even if unpushed — and no auto-memory references it as live); **preserve it first** (rename to `plan-<topic>.md`) **only** when its tasks aren't committed anywhere yet (genuinely unexecuted work). This guard applies on **every** path into Phase 4 — the full-proposal and simple-task shortcuts overwrite `plan.md` too, not just continuation. The spent case is the norm for a `plan-next-issue` sequential run, where the prior issue's committed-but-unpushed plan lingers on disk.
2. Create the branch named in the plan. When the current branch is only a few commits ahead of `origin/<default-branch>` and those commits naturally batch with the new work, prefer `git rebase origin/<default-branch> && git branch -m <new-name>` over spawning a fresh worktree. Spinning up a new worktree for one or two carry-forward commits trades one mechanical step for several.
3. **If continuing on the current branch**, verify it's up to date with the base branch:
   ```bash
   git log --oneline HEAD..origin/<default-branch>   # should be empty
   ```
   If behind, fast-forward (`git merge --ff-only origin/<default-branch>`) before starting. Stale-base execution produces a PR diff that mixes the plan's changes with upstream-merge noise. **If refreshing `origin/<default-branch>` needs a `git fetch` that fails on interactive auth** (e.g. a 1Password SSH agent prompting while the user is away → `Permission denied (publickey)`), the refresh is read-only — confirm the cached tracking ref is current over the host API instead of stalling: for `repo.host: github`, `git rev-parse origin/<default-branch>` equals `gh api repos/:owner/:repo/commits/<default-branch> --jq .sha` (HTTPS, no SSH) means `origin/<default-branch>` already matches the remote, so run the `HEAD..origin/<default-branch>` behind-check above as normal against it; other hosts have their own read-only commit API. (Compare the **tracking ref**, not `HEAD` — `HEAD` is your work branch, which is legitimately ahead.) The push (later) still needs the user; only this read falls back.
4. **Write the pre-committed acceptance criteria** — after the branch exists, before the prep commit. This step wholly precedes Execution's first implementer dispatch. **Determine the target issue** via a fallback chain: the `#N` referenced in the task description → a `plan-next-issue` handoff → the requirements doc's issue reference → else this is an issue-less run. **Every link in that chain resolves an issue that already exists — so if Phase 2 split the work, the chain is stale by construction:** the task description's `#N` is now the parent, and criteria written there would pledge the parent against one child's scope. Use the split issue this plan is for, filed back in Phase 2. Do **not** fall through to the issue-less branch because the number feels uncertain — a wrong-but-existing `#N` and a missing `#N` fail differently, and only the second is what that fallback is for. **The chain can also resolve more than one existing issue** — a `plan-next-issue` handoff for a combined plan names every selected issue (see that skill's §3), and a user can name several directly — which is the *opposite* of the split case above (nothing is stale, every target already exists, nothing new is filed): route this to the **Multiple target issues** bullet below, which picks a **canonical** target, rather than writing to the first `#N` found.
   - **Issue present — one target issue (primary, Home B):** fetch the current issue body via `bugTracker.readOne` (e.g. `gh issue view {id} --json body`), construct the updated body per *"Writing the section into an issue body"* below, and write it back with the host-native edit command for `bugTracker.kind` (e.g. `gh issue edit {id} --body-file {tmpfile}`, following `triage-issues`' body-file pattern — that pattern covers *only the write* and says nothing about how the preserved body it writes gets constructed). **Best-effort per `development-principles.md` principle #9:** if the write is blocked (auto-mode write-classifier denial, or no user present for a permission prompt), don't drop it — surface the fully drafted `## Acceptance Criteria` checklist so the user can apply it (`! gh issue edit …`) and record it as an outstanding action.
   - **Multiple target issues (combined plan):** when the chain above resolves more than one existing issue (never "one or more" — exactly one target stays on the *Issue present* bullet unchanged), dedupe the target list and pick the **canonical**, the target with the lowest issue number — the canonical is never its own sibling, so every other target in the deduped list is a sibling by construction. Write the checklist once, to the canonical only, constructing and writing the updated body per *"Writing the section into an issue body"* below. **The section must open by naming every issue the plan spans** — that line is what makes the whole pledge reachable from a sibling, and it tells a reader the checklist deliberately exceeds the issue they are looking at. **Ordering is load-bearing per `development-principles.md` principle #12:** the canonical write must land before any sibling pointer, since a pointer asserts the canonical already carries the section. Once the canonical write lands, comment on each sibling with the host-native comment command for `bugTracker.kind` (e.g. `gh issue comment {id} --body "Acceptance criteria for this work are pledged on #<canonical>."`) — a comment only, **never** a second body section, so no sibling's body is touched and no issue gains a second acceptance-criteria heading. **A sibling's own pre-existing acceptance-criteria section is left untouched** — it is that issue's own filed acceptance, not this plan's pledge, and the pointer comment is what tells a reader where the pledge actually lives. **Best-effort per `development-principles.md` principle #9, reported per issue rather than as one failure:** if the canonical write is blocked, surface the drafted checklist and every drafted pointer comment and write none of them; if the canonical write lands but a sibling comment is blocked, surface that comment's text naming the issue it belongs on and record it as an outstanding action.
   - **Issue-less (fallback):** write `docs/acceptance/<slug>.md` (slug = the plan's kebab-case branch name) containing the checklist under the canonical `## Acceptance Criteria` heading, replacing the file's whole content rather than splicing a section into it, and self-index it into `docs/TOC.md` under a conventional heading — the same scaffold-on-first-use pattern `docs/decisions/` follows below (offer interactively, auto in `--non-interactive`, idempotent, skip gracefully if `docs/TOC.md` is absent). This bullet is exempt from the splice rule below: a whole-file replace makes the one-section invariant hold trivially — one file, one section, nothing else in the body to preserve — and it needs no supersession mapping either, because the file is git-tracked and `git log -p` on it recovers any content a rewrite superseded, unlike a `gh issue edit` whole-value write, which leaves no diff view of what it replaced.
   - **The fallback file is a tracked companion doc**, not a local-only artifact: fold it into step 5's gitignored-`plan.md` exception — when `plan.md` is skipped because it's gitignored, `docs/acceptance/<slug>.md` (like an ADR) still gets committed in the prep commit.

   **Writing the section into an issue body:** these rules govern the acceptance-criteria write for both tracker branches above — *Issue present* and *Multiple target issues* — whichever one supplies the canonical body; the *Issue-less* bullet above is exempt from them, as it states.

   **Match tolerantly on the way in; write the canonical heading back out.** Look for an existing section by matching a `##`-level heading whose text — lowercased, with trailing punctuation stripped — reads `acceptance criteria`, `acceptance criterion`, or a straightforward singular/plural variant. Match at line start only, and ignore any match that sits inside a fenced code block — issue bodies routinely quote markdown, including this skill's own text. Match `##` only: a `###` sub-heading, or a heading carrying extra words such as `## Acceptance criteria (proposed)`, is a near miss, not a match, and routes to outcome 3 below rather than being guessed at. Tolerance runs inbound only — whatever spelling you matched, write the section back under the exact canonical `## Acceptance Criteria`, so the body carries the heading `gvt-dev:validator` and `gvt-dev:code-reviewer` look for. A strict match would instead treat `## Acceptance criteria` as a different heading from `## Acceptance Criteria`, append beside it, and leave two near-identical checklists in one body — neither grader can tell which one it's grading, and a reader of the closed issue can't tell which the work was pledged against, the exact ambiguity ADR-0017 exists to remove.

   **Write so that the body carries exactly one acceptance-criteria section when this step completes — per body, not per plan.** For a combined plan, only the canonical body carries the section; every sibling carries a pointer comment and no section of this plan's making. The match above resolves to one of three outcomes:

     1. **No existing section** → insert the emitted checklist under the canonical heading.
     2. **An existing section this checklist supersedes** → replace it in place, and open the new section with a mapping from old items to new (`orig-1 → R1+R2`, `orig-2 → R4`, …), naming by number any criterion the original could not have contained — typically one arising from a planning-time premise correction — rather than letting it blend in. The mapping is what lets a reader verify nothing was dropped: this is a whole-value write with no diff view, so an unmapped drop is invisible.
     3. **An existing section this checklist does not cover** — it encodes acceptance this plan deliberately scoped out, or it's a near-miss heading from the paragraph above → surface it at the checkpoint as an explicit fork. Never silently discard it, never silently keep it beside the new one. If the body already carries two matching headings, collapse them to one and report it.

   **Splice on headings, never on line numbers.** Build the new body from three parts: the prefix is everything before the matched heading line; the span runs from that heading to the next line beginning `## ` (or to the end of the body, if there is none); the suffix is that boundary line onward. Emit prefix, then the new canonical section, then suffix. When nothing matched above, the prefix is the whole body and the suffix is empty — that is the append case, same rule. Never derive the splice from line numbers: a `grep -n` offset fed into a `head`/`sed` range is valid only for the body you read it from, and one extra line, or a second `## ` arriving sooner than expected, silently truncates a live tracker issue while the edit command reports success. Assemble the three parts with the session's own file-reading and file-writing tools, not a shell text-processing pipeline — this skill declares only `git` as a required tool. Before writing, read the assembled body back and confirm the tail you meant to preserve is still there.

   **This write is the only edit of that body this plan schedules.** If the run also schedules a body edit — a task the planner emitted to annotate scope discovered during planning, or the *reconcile the issue body in the same PR* instruction the superseded-mechanism gates give in Phase 1 and in the full-proposal shortcut — fold its content into this write and drop the separate task. Two `--body-file` round-trips against one body carry no ordering guarantee and no pathspec equivalent to scope them down: the second call reads its own copy of the body first, and if that read happens before the first edit lands, the second write clobbers it without any error surfacing — the identical shared-target failure the explicit-pathspec rule polices for the git index, except there is nothing here to defend it. Merging avoids the race entirely and leaves a cleaner artifact besides: one edit carrying the pledge and the scope correction together, instead of two edits where the later one looks like it undid the earlier one. A scheduled edit aimed at a sibling is a different case: a sibling has no acceptance-criteria write to fold into — a sibling gets a comment, not a checklist. If that sibling's body genuinely needs the edit, it stands alone as that body's only scheduled edit, lands after the sibling's pointer comment, and never adds an acceptance-criteria section; otherwise carry its content in the pointer comment instead. This scoping is per plan, not per session: an earlier skill in a chained run — `triage-issues` rewriting a body during triage, say — may already have edited it, which is why this write always starts from a fresh `readOne` rather than trusting an earlier phase's read.
5. **Commit the plan and any companion design docs as a single prep commit** before kicking off the first implementation task. This keeps git history in logical order (`prep → task 1 → task 2 → ...`) and prevents retroactive plan commits from landing after tested code. **Exception:** some repos gitignore `plan.md` (or the planning location) so it stays a local-only working artifact — check `git check-ignore plan.md` first. If it's ignored, that's intentional; don't force-add it. Skip the prep commit (or commit only the tracked companion design docs, including a `docs/acceptance/<slug>.md` fallback from the step above), and keep `plan.md` local.
6. **Author a decision record when the ADR threshold is met.** Durable architecture and compromise rationale must survive the transient `plan.md` — capture it in a committed decision record (see `${CLAUDE_PLUGIN_ROOT}/docs/development-principles.md` principle #7).
   - **ADR threshold — author one when a non-trivial design decision was produced**, regardless of which phase or checkpoint surfaced it: Phase 2 (Design) running, or the simple-task/full-proposal shortcut's `AskUserQuestion` checkpoint resolving a design fork, are both equally qualifying origins. It's not *whether the formal designer ran* that gates the ADR — only *whether a non-trivial decision was made*. A decision qualifies when it made a **cross-module/architectural or mechanism choice**, *or* rejected an alternative that **differed in surface** — which file, component, or contract owns the change — rather than merely in **scope width** (how much of the same shape to do). **Skip** the record otherwise: trivial or cosmetic changes, shortcut tasks that resolved no genuine fork, and the width-only case above.
     - **The surface-vs-width tiebreak is what resolves the common ambiguity**, because "purely additive" describes the *change's shape* while "an alternative was weighed" describes the *decision process* — both are routinely true at once, so neither alone settles it. *"Should this guidance live in the skill body or in the shared `development-principles.md`?"* changes which component owns it → **surface**, author the record. *"Just the skill, or also a cross-reference pointing at it?"* is one shape at two widths → **width**, skip. When a purely-additive change turns on a surface choice, the record is still warranted; the additive shape is not itself grounds to skip.
   - **When the threshold is met:** dispatch `gvt-dev:tech-writer` to author `docs/decisions/NNNN-*.md`, handing it the design doc's architecture + compromise sections and the originating issue reference. tech-writer scaffolds `docs/decisions/` (and a `docs/TOC.md` entry) on first use, names the record, fills the template, and back-links the issue. Commit the record together with the prep commit (or as the first task's commit when `plan.md` is gitignored) — **unless the record's content depends on something execution produces**, most commonly a follow-up issue number for a deferred-scope decline; in that case author and commit the record *after that dependency resolves*, and say so in the plan's task ordering — a recorded deviation, not a silent one. **Never author an ADR against a placeholder or predicted issue number** — the same soft-reservation hazard that governs the record's own number (below) applies equally to any number the record cites. **Dispatch tech-writer directly — do not route this through `gvt-dev:create-adr`.** That skill is the on-demand path for recording a decision *outside* a plan run, and it owns its own commit: its final step confirms the staged set with `git status` and commits it. Inside an execution that stages concurrently, that sweep captures sibling tasks' staged files and lands them in the ADR commit — the same hazard the explicit-pathspec rule below guards — *"Whenever more than one task's changes sit in the git index at commit time, commit with explicit pathspecs."* Supply the record number explicitly (re-resolved against `docs/decisions/` at authoring time, since a number minted earlier in an issue body is a soft reservation nothing detects going stale) and instruct tech-writer to stage only.
   - **Never fabricate a backfilled record's date.** When the decision was actually made *earlier* than this PR (a backfill, or a decision predating the ADR convention), instruct tech-writer **not to invent a `Date:`** — fabricated dates (e.g. placeholder `2024-01-01`/`2025-01-01`) are worse than none. Derive the date from the git history of *the code the decision is about* — **not** the new ADR file, whose first commit is this PR: `git log --diff-filter=A -- <decision-file>` for when the relevant file first appeared, or `git log -S'<symbol>'` for when the decision's symbol/pattern was introduced. If it can't be pinned to a day, **hedge to month/year — never guess a day.** Distinguish **Originally decided** (the real decision date, from git history) from **Recorded** (when the ADR file was written — i.e. this PR's date) so a backfill is honest about both.
7. The plan is now ready for execution.

### Dispatch resilience

Every phase above (and every implementer dispatch during execution) is delegated to an agent that can come back empty — it errors, or hits a session/token limit and returns an empty final message (`subagent_tokens: 0`). When that happens, **do not retry blindly or stall**:

- **Resume the same agent via `SendMessage` when that tool is available** — this reuses its accumulated context and is the cheapest recovery.
- **Otherwise, complete the phase inline from the prior phase's artifact.** The requirements doc, design doc, or the concrete touch points you already gathered usually carry enough to finish the next phase directly. Write the missing output yourself and continue, rather than re-running the whole dispatch from scratch.

### Verified vs. inherited facts in a dispatch brief

**Every dispatch brief separates two buckets of fact, and carries each labeled as such.** The first bucket is *facts verified against the artifact this run — do not re-derive, but flag if you find them wrong*, each carried with the evidence that established it (the file, the command, the exact text read). The second is *facts inherited and not verified — yours to check if you rely on them*. Collapsing the two into one undifferentiated brief is what lets a stale or misremembered fact ride along as if it were current.

**The test for "verified" is narrow: a claim counts as verified this run only if this run read the artifact it describes.** A claim that was corrected, reformatted, summarized, or reasoned about is **not** thereby verified — only re-derivation from the source, this run, earns the label. A fact copied forward from an earlier phase's brief, or restated from memory of an earlier read, belongs in the inherited bucket even if it happens to still be true.

**Label, don't omit.** Carrying an uncertain fact under a label beats dropping it: an omitted fact is a silent gap the receiving agent has no way to notice, while the label is what actually triggers the check. **This is reasoning, not a demonstrated result** — the trial behind this change ran a labeled arm and a flat-assertion arm and observed that labeled claims got checked while flatly-asserted ones did not; it never ran an omit arm, so don't cite it as proof that omission is worse than a label — only that a flat assertion is.

**A predicted value is a third bucket — neither verified nor inherited, but the orchestrator's *hypothesis* about what the task will produce** — an expected finding count, an expected file list, an expected pass/fail split. Label it as a hypothesis, because unlabelled it reads as a target, and the failure is an implementer quietly adjusting its work until the number matches: the same shape `## Execution` names in *"A task that authors its own verification tool can pass by shrinking the tool's field of view"*, except the pressure arrives from the brief rather than from the schedule. So the brief **pre-authorises contradiction** in substance: *report the difference with the evidence and stop short of changing the code to match my table — my table is a hand-read hypothesis, and a disagreement is at least as likely to be my error as yours.* **Reporting a mismatch is the expected outcome, not an escalation.** The asymmetry is what makes this worth the words: a prediction that turns out right costs one sentence, while one that turns out wrong and went unlabelled is adopted silently. (Observed on the run that added this: four orchestrator errors were caught by implementers *because* their briefs marked expectations as hypotheses — among them a predicted finding count of 126 that was really 128, the orchestrator's premise about which citations counted as findings being simply wrong, and a vacuous acceptance criterion an implementer refused to write as specified. Two of the four would otherwise have shipped.)

**The correction-pass trap: correcting an issue's periphery is exactly when its central mechanism is *least* likely to be re-checked.** A pass that fixes four real defects manufactures confidence in the fifth claim, which was never actually read this run — the visible progress on the other four makes the fifth feel covered by association. Treat a subagent's correction as a likely find rather than noise — verify it, but expect it to be right, rather than discounting it because the rest of the pass looked clean.

**Tracker and PR state decays faster than code facts.** An issue's open/closed state, whether a PR merged, a label's current value — these can change between the moment a fact was gathered and the moment the brief is written, in a way a source file's content does not. Re-read tracker/PR state at dispatch time rather than inheriting it from earlier in the session.

**This governs every dispatch this skill makes** — Phase 1 (analyst), Phase 2 (designer), Phase 3 (planner), and every implementer dispatch during Execution — the same all-phases scope `### Dispatch resilience` above opens with.

## Execution (Post-Approval)

**plan-task owns the commit.** The validator gate is only meaningful *before* the commit, so implementer dispatches return their changes **staged but uncommitted**; the orchestrator runs the validator and commits only on pass. This blocks a failing task from landing committed and gives uniform commit authorship across the plan. Tell every implementer dispatch explicitly: *stage the specific files you change, but do not commit — I run the validator and own the commit.* (Implementer agents like `ts-implementer`/`tech-writer` read their dispatch prompt to pick standalone vs. orchestrated mode; giving the instruction explicitly is what selects orchestrated mode, rather than relying on their default — which is standalone.)

When the user says to execute:

1. **Check git log** — compare commit messages to plan tasks. Don't re-implement already-committed work.
2. **Delegate tasks** to the implementer agents per the plan's domain assignments, **instructing each dispatch to stage its files but leave them uncommitted**. Use `gvt-dev:ts-implementer` for TypeScript or JavaScript work (including plain ESM `.mjs`, e.g. this plugin's own audit scripts); the project may have additional domain-specific implementer agents listed in `CLAUDE.md`.
3. **Run `gvt-dev:validator`** on the staged changes after each implementation task — it now also checks the staged diff against the recorded `## Acceptance Criteria`. **For a combined multi-issue plan, name the canonical issue explicitly in the dispatch** — `bugTracker.readOne` fetches a single `{id}`, and only the canonical body carries the checklist; every sibling body carries just a pointer comment. A row marked **`[not-yet-due]`** is out of scope for branch review — the validator reports it, neither grading it unmet nor omitting it. A row marked **`[point-in-time]`** is checked at the gate where its moment falls, and its verdict recorded there — not deferred to a later sweep, since after merge its evidence is gone and it can never be re-run.
4. **Commit on pass** — the orchestrator makes the commit (using the project's commit format) only after the validator passes. If it fails, fix forward (re-dispatch or correct) and re-validate before committing; nothing red gets committed. **One-commit-per-task is the default, not a rule against batching:** when several tasks refine the *same* file (common for doc/skill edits), committing them together as one logical commit is cleaner than patch-staging to force a commit each — the goal is a readable history of logical changes, not a 1:1 task-to-commit mapping.

   **Known-red baseline for intentionally-red TDD steps.** Some plans intentionally sequence a red step — a golden/snapshot fixture changed in an early task but regenerated in a later one, or a TDD prep step that adds a failing test before the task that wires it up. Running the full validator after each of those earlier tasks would keep reporting that expected red, drowning real signal and tempting "commit anyway." Instead: before execution begins, record the expected-red set (the checks the plan's labeled steps intentionally leave failing, per the planner's labeling — see `plugin/agents/planner.md`). The per-task gate then blocks only on **new** red this task introduced beyond that recorded baseline, not the pre-existing intentional red. Gate each earlier task on typecheck plus that task's own targeted tests (which its done-when should already enumerate), and defer the full-suite/golden gate to the regeneration task and the final validation gate. This carves out the *intentional* red only — it does not loosen the gate for genuine regressions; "nothing red gets committed" still holds for anything outside the recorded baseline. **This block has a blind spot worth naming: a check that is green from the start never enters the recorded expected-red set, because there's no red moment to record it at** — so it sits structurally outside this block's reach, which is exactly where an unfalsifiable assertion hides undetected.
5. **Run `gvt-dev:code-reviewer`** at the end, and tell it explicitly which diff to grade — by the time this step runs, step 4 has already committed every task, so `git diff --staged` is empty; point the dispatch at the branch diff against the base instead (e.g. `git diff <base>...HEAD`, or the PR diff) rather than leaving the comparison to the agent's default. If it flags doc gaps, offer to dispatch `gvt-dev:tech-writer` (same staged-but-uncommitted protocol — you commit its doc changes after review). **For a combined multi-issue plan, this dispatch also names the canonical issue explicitly** — the same single-`{id}` `bugTracker.readOne` fetch applies, and only the canonical body carries the checklist siblings are pledged against. The validator gate above and this one share the same blind spot on timing, so they share the fix: a **`[not-yet-due]`** row stays out of scope here too, and a **`[point-in-time]`** row is graded now, at this gate, not deferred to a later sweep. **Close the run with the criteria coverage — N rows pledged, N graded, naming which were verified, which are `unverifiable-as-written`, and which are out of scope and still owed after merge.** None of this ticks a box automatically: it is marking and reporting only. A criterion that could not be verified is reported, never ticked.
6. **File deferred-scope follow-up issues best-effort — draft always, create best-effort.** If execution deferred scope to a follow-up issue, draft its full body (title, labels, body) as part of closing out; the `gh issue create` itself is best-effort. If the create is blocked — the auto-mode write-classifier denies it (a `Bash(gh issue *)` allow-rule does **not** override that gate), or a permission prompt fires while the user is away — surface the drafted body so the user can file it (`! gh issue create …`) and record it as an outstanding action rather than letting it drop (see `${CLAUDE_PLUGIN_ROOT}/docs/development-principles.md` principle #9).

*The index is shared — a co-staged task's work is entangled with its siblings'*

**Whenever more than one task's changes sit in the git index at commit time, commit with explicit pathspecs.** Two legitimate patterns put multiple tasks in the index before you commit: independent tasks *dispatched in parallel* (see `superpowers:dispatching-parallel-agents`, to cut wall-clock), and several independent tasks *batched into one implementer dispatch* (common for doc/prose plans — one `tech-writer` call editing five separate files saves the per-task subagent spin-up). Both are fine; only tasks that share a file, or where one's output feeds another, must stay sequential in their own dispatch. Either way the staged-but-uncommitted protocol has a sharp edge: every task stages into the **same git index**, so a bare `git commit -a` / `git add -A` at the end of one task **captures the sibling tasks' staged files too**, landing them in the wrong commit. Commit each task with **explicit pathspecs** (`git commit <that task's files>`) so the commit contains only its own work — this is the norm for a batched dispatch, not just a parallel one. And note the per-task validator gate then sees the **union** of all co-staged changes — it can't isolate one task — so keep co-staged tasks genuinely independent and lean on the **final full-tree validate + end-of-run `code-reviewer`** as the real safety net rather than the per-task gate.

**A co-dispatched agent's reading of the index is a snapshot mid-race — never trust its report about a *sibling's* files.** The hazard above is about writes; this one is about reads, and it survives every pathspec discipline. Concurrent agents finish staging at different moments, so an agent that runs `git status` to confirm its own work also sees a **partial** view of everyone else's: a sibling's file legitimately shows as untracked or unstaged simply because that sibling hasn't finished yet. Two consequences. First, **verify co-staged state yourself before committing** rather than assembling it from the agents' reports — the reports disagree, and the disagreement is not evidence that anything went wrong. Second, and worse, **tell each dispatch not to act on what it observes about files outside its own task**: an agent that reads a sibling's not-yet-created file as *missing* can helpfully create it, producing a duplicate or a clobber that no pathspec at commit time will catch, because by then the damage is inside the sibling's own path. (Observed 2026-08-07: two `tech-writer` tasks co-dispatched for an ADR and a CHANGELOG entry; the second reported the first's ADR as untracked and its `docs/TOC.md` edit as unstaged. Both were in fact staged — the report was simply taken before the sibling finished. Harmless only because the orchestrator re-checked `git status` itself instead of believing it.)

**Any command the orchestrator runs to verify an implementer's work must read the index, not the worktree — and a verification that reports "nothing wrong" from an empty corpus is not a pass.** The staged-but-uncommitted protocol above means the worktree is clean by design while a task's own changes sit staged in the index; a verification command aimed at the wrong tree will find nothing to complain about no matter what happened, which reads as a clean pass while proving nothing. The cheap tell: `git diff --staged --numstat <path>` printing nothing means *the file is not staged*, not *the file is unchanged* — confirm the path actually appears in `git status --porcelain` (or `git diff --staged --stat`) before trusting a zero-output check.

**The union also invalidates any *whole-suite absolute number* in a co-dispatched task's done-when.** "Full suite → `pass 220`, count unchanged" is a sound criterion for a task run alone and **wrong by construction** the moment a sibling adds tests: the number moves for a reason that has nothing to do with this task, and the implementer either reports a false failure or spends the effort proving the delta belongs to someone else. Scope a co-dispatched task's numeric criteria to **its own files** — its own test file's count, `git diff --staged` (never a bare `git diff` — the staged-but-uncommitted protocol above means the worktree is clean and a bare `git diff` reports nothing regardless of what the task actually touched, which is a check that cannot fail) on the specific paths it must not touch — and keep suite-wide totals for the final validation gate, where the union is the whole point. If a task genuinely needs a suite-level assertion, state it as a **direction** ("`fail 0`; total pass count increases by this task's new tests") rather than an absolute, since direction survives co-staging and an absolute does not. This is the same shape as the known-red baseline above — gate the task on what the task controls — and it applies to any global tally, not just test counts.

*What an implementer authored does not certify itself*

**An implementer's authored technical claims are output, not report — verify the ones that ship.** Where a dispatch supplies concrete facts (a probe table, measured figures, an enumerated case list) and asks the agent to render them as prose — a docstring, an ADR, a commit body — diff the rendered claims against the source data before committing. A paraphrase can invert a boolean or drop a qualifier while reading fluently, and no test, linter, or type-checker examines comment prose, so every automated gate stays green. Rationale comments are the sharpest case: they exist to steer a future reader, so an inverted reason argues *for* the change it was written to prevent. This is the discipline the Phase-2→3 handoff already requires when it says to pass the designer's `## Test Criteria` table through verbatim — applied one handoff later, where the prose is actually authored. (Observed as construct3-chef#160: a probe-verified table gave `entry.isFile()` as `false` for a junction, while the shipped docstring said `isDirectory(): true` — inverting the paragraph's own argument, so it argued for the very simplification it existed to prevent. Lint, typecheck, 1512 tests, and a code-reviewer pass that explicitly graded "docstring factual accuracy" were all green.)

**A task that authors its own verification tool can pass by shrinking the tool's field of view.** When a task both builds a check and is graded by that same check, the gate is only as honest as the tool's scope — and scope is exactly what the implementer controls, so a task under schedule pressure can narrow it without ever writing a false line. Never let such a done-when be graded **solely** by the tool the same task authored; pair it with a **red→green transition on a pre-existing, independently-known defect** the tool must catch, or with a **corpus the agent does not choose**. Read the tool's **scoping decisions** — what it walks, what it excludes, what counts as a hit — not just its output; a clean report proves nothing about a tool whose walk was quietly narrowed to avoid the hard case. The cheap smell to check first: a **reported item count that does not match the corpus the row names** — `checked=44` reported against a file that contains 9 links is the tell, not the 0 failures next to it. Where narrowing the scope is legitimate, require a unit test pinning the **negative** case — the defect is invisible under scope A, visible under scope B — or the narrowing's effect on semantics regresses silently the next time someone touches it. This is the scope variant of the known-red baseline's own blind spot above (*"a check that is green from the start never enters the recorded expected-red set"*) — that gap is about timing, never having a red moment to record; this one is about breadth, never having a corpus wide enough to turn red at all.

*A later step can falsify an earlier claim*

**Same blind spot, later trigger: a task can falsify a comment an *earlier* task in this plan wrote.** When a task changes behaviour that an earlier task described in a comment or docstring, re-read that prose before committing. The suite will not tell you — the assertion the comment sits above is typically unaffected either way — and only the orchestrator has the whole-branch view this needs: the implementer executing the later task never saw what the earlier one wrote, and the planner could not know at plan time which comments would be authored. (Observed in c3-domain-manager: task 3 documented that two surfaces were "not yet reconciled"; task 4 reconciled them — the whole point of the plan — and the comment was false one commit later, with the suite steady at 350 passing / 0 failing.)

**The same shape, higher stakes: a later task in *this same plan* can falsify a pledged acceptance-criteria row, not just a comment.** The paragraph above is scoped to comments and docstrings, whose worst outcome is a misleading local read; a pledged criteria row is graded by two independent critics and written into a tracker issue, where it outlives the branch entirely. The common shape is an **absence row** — a zero-hit or "never mentions X" criterion — over a token a later CHANGELOG entry, ADR, or issue-comment task in this same plan must **legitimately** go on to name. `designer.md`'s Test Criteria rule for whether a row's expected value can coexist with the change's own deliverable (the bullet opening *"Is the expected value right?"* in its authoring step) states the authoring-time half of exactly this tension, for prose the design itself is about to write; this is the execution-time counterpart, scoped to *this plan's own remaining tasks* rather than to prose already on the page when the row was authored. Before the final gate, re-run every absence row in the checklist and ask whether any task still ahead in this plan will introduce a legitimate mention of the token it bans. Where one will, the remedy is the same one the count-and-zero rules above already prescribe: **re-scope the row to the surface where the defect actually lived, keeping a baseline**, rather than leaving it as written. Both easy exits are bad and named as such: relaxing the criterion defeats the pre-commitment ADR-0017 exists for, and deleting the citation the later task would otherwise write leaves a worse-documented artifact than doing nothing.

*The pledged target itself can be defective*

**A pre-committed criterion found defective during execution is amended in the open, never quietly.** ADR-0017's pre-commitment means the target cannot move *silently*, not that it cannot move at all — a criterion can be wrong in a way only execution surfaces, and refusing to touch it produces theater, not rigor. Four properties hold together: **(1)** before touching the row, verify the **protected requirement** — the thing the row exists to establish — by a check **independent of the row's own literal**, so the fix corrects the measurement rather than quietly loosening the target it was meant to hold. **(2)** record the amendment in the **durable acceptance-criteria artifact** — the issue body itself, not only the session transcript — carrying the original expectation, the defect found, and the evidence that established it. **(3)** surface the amendment to the reviewing gate explicitly, so the amendment is itself graded rather than silently absorbed into an otherwise-passing run. **(4)** name which failure mode this is, because the three read alike from outside and call for different fixes: **defective** (wrong the moment it was written — never true), **decayed** (right once, the tree moved under it — the Phase-3 correction rule above), or **unmet** (the row is fine; the work behind it simply isn't done yet). Conflating any pair of these — amending a merely-unmet row instead of finishing the work, or treating a decayed row as if it were defective — misdiagnoses the fix.

## Shortcuts

For **simple tasks** (single-file, obvious implementation), compress the pipeline:

- Skip the analyst — state requirements inline
- Skip the designer if the approach is obvious
- The planner can produce a minimal plan directly
- Run the validator gate inline (the project's `validate` command directly) instead of dispatching `gvt-dev:validator` when the change is trivial and deterministic (e.g. a single-line doc edit) and a full subagent per commit would cost more than it surfaces. Still gate before the commit — only the mechanism is lighter, not the gate. The known-red baseline treatment above applies the same way when the gate runs inline: check the recorded expected-red set before flagging a failure as new.
- **The compressed checkpoint above authorizes Phase 4 only** — the first implementer dispatch still needs its own separate execution approval under `## Execution (Post-Approval)`, taken as its own turn.

For an **issue that's already a full proposal** (rationale + a concrete proposed change/mechanism; open questions optional):

- Treat the **issue as the requirements doc** — skip the analyst. **This shortcut assumes the work is *unbuilt* — verify that assumption first** (apply the Phase 1 feature-already-shipped / bug-symptom-observable / dependency-already-resolved gate above). **Also verify the issue actually contains a proposed *change/mechanism* — not only a problem statement / goal / acceptance criteria — before treating it as the requirements doc and skipping the analyst.** A triaged/enriched label is *not* itself evidence of a mechanism: a problem-+-goal-only issue (even a triaged one) needs the full analyst → designer pipeline, where the design space is explored — skipping it produces a weaker plan. This mechanism-presence gate sits alongside the unbuilt gate. A triaged "full proposal" can still be a tracking issue whose core work already shipped; if so, scope to the open checkboxes or propose closing rather than planning shipped code. **Pattern-divergence claims arrive most often in a full proposal:** when it frames a site as a bug because it diverges from a reference fix/established pattern, apply the bug-observable gate's reference-fix check above — verify the reference targeted an observable reader, don't infer it from the pattern.
- **The shortcut's other gates ask whether the work is *real and unbuilt*; this one asks the prior question — whether the proposal's factual claims about the artifact it modifies are actually *correct*.** A full proposal often prescribes concrete content — replacement wording, a JSON/config shape, a snippet, a schema — and that prescription can simply be wrong about the current state of the file it edits. Before adopting the issue as the requirements doc, read the target artifact and diff the proposal's concrete claims against it. **Both directions are live — do not assume either side is authoritative:** the proposal may be stale or wrong, or the proposal may be right and the artifact has been wrong since it was written; the natural bias is "the issue is stale, trust the file," but the motivating case ran the other way. Name the source that actually settled the conflict — an external spec, git history, or the artifact's own provenance — and when the artifact turns out to be the wrong one, correcting it is in scope for the same PR, not a follow-up. When no such source exists, surface the conflict at the checkpoint as an explicit fork; never silently pick a side. This bites hardest on doc/config/schema proposals, where the prescribed content *is* the deliverable, and the trap compounds because a polished proposal invites copy-paste precisely by looking finished. (Same check as the Phase 1 gate above, applied here at the shortcut's requirements-adoption point; see `development-principles.md` principle #13.)
- **The gate above reads the artifact a proposal modifies; a proposal's *measured* claims have no artifact to read, and re-deriving one means running something.** A benchmark, a platform matrix, a collision rate, a timing figure — these are claims about the world, not about a file, so a planner satisfying the artifact check diligently still sails past a false one. When a cited figure is load-bearing — it justifies choosing one mechanism over another, or it would be transcribed into shipped text such as an ADR, a docstring, or a CHANGELOG entry — re-measure it before adopting the design that rests on it, with `gvt-dev:build-probe`. Structural precision is not evidence of empirical precision: an issue exact to the line number about the code can be badly wrong about the world, and being right about the code makes the measurement feel *more* credible rather than less. A figure that fails to reproduce is not noise to drop silently — correct it in the issue body, say which way the correction cuts (a conclusion can survive a re-measurement that still flips the decision the figure was used to justify), and never let the original reach shipped text, where an ADR or docstring carrying a fabricated number is worse than one carrying none. The same rule covers the non-shortcut path at the Phase 1 gate above.
- **Criteria authored on this path have no designer's table behind them, so the transcription-scoped cross-checks above never attach to them — a row here can be *born* in conflict with a documented convention rather than *decayed* from one that was once true.** Neither of the two gates just above reaches this: the artifact check reads the file the proposal modifies, and the measured-claim check re-runs a figure — neither one asks *how* a criterion says it will be verified. Before writing the checklist to the issue body, identify the convention doc governing the artifact under change (the repo's CLI-script, testing, or schema conventions — `CLAUDE.md` and the doc index name them) and confirm each row's verification method is the method that doc prescribes, not one the issue happened to propose. Get this wrong and the failure is silent and late: the implementer correctly follows the convention, the row grades unmet against what it actually said, and amending it after the fact is exactly the quiet retarget ADR-0017's pre-commitment exists to prevent. This check runs *before* the last bullet below writes the checklist — that bullet owns getting the checklist into the issue body; this one owns confirming what's in it is right first.
- **An *optional* consolidation / DRY item is a candidate, not a directive — check the redundancy against repo precedent before adopting it.** A full proposal often carries an "(optional, DRY)" item: fold N duplicated blocks into one shared reference. Before planning it, verify the duplication is *accidental* rather than *deliberate* — read how the repo already handles the same tension at a comparable site. Established precedent outranks the issue's suggestion, since it encodes constraints the issue author may not have had in view, and the "duplicates" are often tailored per-caller rather than verbatim copies. Surface it at the checkpoint as an explicit accept-or-reject fork with its cost named, rather than silently adopting or silently dropping it; if rejected, record the rationale in a durable place (CHANGELOG or decision record) so the next planner doesn't re-propose it. (Surfaced by #167: an optional item proposed slimming three agent blocks to a pointer at a shared principle, but the repo's established pattern is *cite-and-repeat* — an agent dispatched standalone may never load the shared doc, so each inline copy is load-bearing. Rejected, with the accepted duplication cost recorded.)
- **The same three questions apply to a full proposal's prescribed mechanism, and passing one doesn't clear the others.** Is it current — re-verify against live code and surface "mechanism superseded by \<PR\>" if a later change shipped a different mechanism, reconciling the issue body in the same PR. Is it sufficient — a live, un-superseded mechanism can still be structurally unable to satisfy the issue's own acceptance criteria; check it against those criteria, not only against the code. Was it ever the best option — a full proposal reflects one author's choice, not a weighed set: an absent open-questions section is not evidence of a settled design, and a live fork on axes the author had no reason to weigh (platform portability, dependency footprint, hot-path cost, hermeticity) goes to `AskUserQuestion`, recommended option first, with the trade-off measured. (Same three-axis check as the Phase 1 mechanism gate above, applied here at the shortcut's requirements-adoption point.)
- **When this shortcut hands facts about the issue and the target artifact into the combined checkpoint or a dispatch, label them per `### Verified vs. inherited facts in a dispatch brief` above** — the shortcut compresses the pipeline, not the verified/inherited discipline that governs what any brief downstream of it can rely on.
- **Classify each open question before resolving it** — don't assume every one is a preference choice:
  - **Factual** (answerable from the code/repo — e.g. *"does the client read `result.success` for this handler?"*, *"does it re-query cache X after handler Y?"*) → resolve by dispatching the analyst (or an `Explore`/read-only investigation), folded into the current-state mapping. Do **not** ask the user — they usually don't know offhand, and only the code is authoritative. Asking can produce a worse plan (a factual question that resolves to a no-op once the code is read).
  - **Preference / scope** (a genuine product or design choice) → carry into a single `AskUserQuestion` call, one question per open question, recommended option first.

  Investigate the factual questions; only the preference questions go to `AskUserQuestion`. This replaces dispatching the designer.
  - **An issue with no open-questions section resolves this classification block trivially — there's no fork to classify.** That's exactly where the mechanism gate above earns its keep: nothing in this classification step is triggered by a fork the issue never raised, so its absence is not a signal that the prescribed mechanism needs no check.
- Present a combined design + plan in **one checkpoint**, explicitly flagging any friction the chosen answers introduce. **This checkpoint ends at plan approval, not execution approval** — answering its `AskUserQuestion` authorizes Phase 4 only (saving `plan.md`, creating the branch, writing the acceptance-criteria checklist, the prep commit), never the first implementer dispatch, which needs its own separate, explicit **execution approval** taken as its own turn under `## Execution (Post-Approval)`. This boundary is easy to miss on this path specifically: the canonical statement of it sits in a section this path has already read past by the time it reaches this checkpoint, so nothing here restates it at the point where the crossing actually happens.
- Still produce `plan.md`, a prep commit, one-commit-each tasks, and the validator + code-reviewer gates.
- **Compressing the pipeline does not drop the Phase 3 obligations — run [`approval-and-audit.md`](approval-and-audit.md)'s self-audit checklist at the combined checkpoint.** The shortcut replaces the analyst and designer *dispatches*, not the checks that Phase 3 owns. The one most often lost is **writing the `## Acceptance Criteria` checklist to the issue body before execution begins** (ADR-0017): the criteria feel "already written" because they're in `plan.md`, but `plan.md` is transient and gitignored, so criteria that live only there are gone the moment the next task overwrites it — and reviewers never see what the work was pledged against. Write them to the issue — the **canonical** target when the plan combines several issues, per Phase 4 step 4 — or the `docs/acceptance/<slug>.md` fallback, at the checkpoint, not retroactively after the commits land.

For **continuation** of existing work:

- Read the project's tracking doc (if any) and the prior plan
- Check git log for completed tasks
- **Guard against a stale gitignored `plan.md`.** A gitignored plan lingers on disk after its branch merges, so an existing `plan.md` may describe *already-shipped, unrelated* work. Before treating it as continuation, confirm it maps to the current task — its branch is unmerged and its tasks aren't already in `origin/<default-branch>`'s log. If it's stale, treat the new work as a fresh plan — but **don't blindly overwrite a stale plan; first classify what kind of stale it is:**
  - **Already-shipped** — its branch is merged, its tasks are in `origin/<default-branch>`'s log, and no auto-memory references it. Overwrite freely.
  - **Spent (executed this run/session)** — its tasks are already **committed** (the plan's branch exists and `git log` on it shows the implementing commits), even if that branch isn't pushed or merged yet. A `plan-next-issue` sequential run is the common case: it leaves each finished issue's gitignored `plan.md` on disk — the file survives the `git checkout` to the next issue's branch — so the lingering plan is *spent*, not pending. Overwrite freely. The discriminator is *are the plan's tasks committed **anywhere**?*, **not** only *is the branch merged to `origin`?* — a committed-but-unpushed plan is done work, not WIP to protect.
  - **Unshipped / pending** — its tasks **aren't committed anywhere yet** (genuinely unexecuted work-in-progress), *or* a project auto-memory points at it as the live task list. This is an active artifact: **preserve it first** (rename to `plan-<topic>.md`) before writing the new plan, so you don't silently destroy pending work. (A gitignored `plan.md` is local-only, so an overwrite is unrecoverable — there's no git history to fall back on.)

  Either way, don't *resume* the stale plan as if it were this task's plan.
- If a `plan.md` exists with unexecuted tasks:
  1. Spot-check a few representative items from the plan against the current code to confirm they haven't drifted
  2. Present a brief summary: "Plan exists for X, Y tasks remaining. Ready to execute?"
  3. Skip the analyst — the plan is the requirements
  4. Skip design/planning unless the user flags issues
- If no plan exists or the approach changed, start from the next pending task — don't re-run analysis/design unless needed.

## Key Principles

See [`${CLAUDE_PLUGIN_ROOT}/docs/development-principles.md`](../../docs/development-principles.md) for the full philosophy. Quick reference:

- **Iterative** — decide on what you know, work on what you decide, validate what you've done, investigate what you don't know.
- **MMMSS** — many much more small steps. Small steps beat large leaps.
- **Make the change easy first** — preparation (refactoring, tooling, tests) before the feature.
- **TDD with refactoring first** — if the test is hard to write, the design needs work.
- **The plan will change** — stop and reassess when reality contradicts a hypothesis. Scope is a beacon, not a driver.
