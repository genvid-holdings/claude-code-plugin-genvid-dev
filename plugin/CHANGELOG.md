## [4.21.0] - 2026-08-24

### Added

- **`audit-conventions` gains a fifth content scan, `pointer-anchor`: a citation that names a line number must carry a content anchor, and that anchor is resolved against the cited file (#406).** A positional citation — a file path followed by a line number — is a pointer whose target moves whenever anything above it is edited, and until now nothing detected the drift: the citing sentence still reads plausibly while the number silently lands on unrelated text. The scan requires every positional citation to be followed **immediately** by a content anchor — a quoted span, a backticked identifier, or a colon-introduced quotation — naming what the cited line should contain; it then resolves the cited path to a real file and checks that the anchor is actually at the cited line. An anchor found elsewhere in the target reports as **drift, carrying the corrected line number**; an anchor absent from the target entirely reports as **broken**. The asymmetry is the point: a reference carrying an anchor and *no* line number is not a pointer under the grammar at all, so it **cannot decay from renumbering** — the failure mode the scan exists for — which makes the renumber-proof shape the cheapest way to comply, the remedy `ADR-0037` decision 4 and `ADR-0042` already reached, now enforceable rather than advisory. What that shape does *not* buy is anchor verification: never being a pointer, it is never resolved against its target, so its quoted text is unchecked — a deliberate trade of a verified-but-fragile citation for an unverified-but-stable one, recorded as such in `ADR-0047`. Severity is `error`, under the same author-time gate as the principle-citation check, so it can only ever fire against this repo's own corpus. Because `error` against a corpus that does not conform yet would make every pre-existing citation a blocker on unrelated work, the scan ships with a repo-root **ratchet baseline** plus a companion generator script: recorded debt passes, anything new does not. Nine stale citations across the ADR corpus were corrected in the same change. Reference `ADR-0047`. Behavioral skill/agent change → version bump at release.

### Changed

- **`designer`'s expected-value checks gain an emission-surface axis, and `plan-task` names an orchestrator's prediction as a third kind of fact in a dispatch brief (#435, #436).** A criterion asserting over a program's **rendered output** can be vacuous while its pattern and its corpus are both exactly right, because the artifact being grepped cannot carry the token at all: a row pledged as the non-vacuous proof that a gate still fired asserted the run must produce no `pointer-anchor` output, but the report renderer emits each finding's `detail` string and never its `kind` — a report carrying 138 pointer findings counts 0 occurrences of that token, so the row would have graded green with the gate deleted. The new bullet names the tell (a row naming an internal identifier — a finding kind, an enum member, an error class — the user-facing renderer never prints) and rules that a positive control over the **corpus** does not settle it: the control must run through the **same rendering path** the assertion greps, or it proves the property exists while the assertion still cannot see it. Separately, `plan-task`'s verified-vs-inherited section covered two buckets and had no name for a third claim every brief carries — the orchestrator's **prediction** of what a task will produce (an expected count, file list, or pass/fail split). Unlabelled, a prediction reads as a target, and an implementer can satisfy it by adjusting its work until the number matches — the same shape `## Execution` already names for a task graded by the verification tool it authored, with the pressure arriving from the brief instead of the schedule. A prediction is now labelled as the orchestrator's hypothesis, the brief pre-authorises contradiction and states that a mismatch is at least as likely the orchestrator's error, and reporting one is the expected outcome rather than an escalation; the asymmetry is the justification, since a right prediction costs one sentence and a wrong unlabelled one is adopted silently. Behavioral skill/agent change → version bump at release.

## [4.20.0] - 2026-08-22

### Changed

- **A criterion's integrity obligations now attach to the criterion itself, not to the path that produced it — and a pledged criterion found defective during execution is amended in the open (#378, #398, #299, #269, #392, #391).** Every integrity rule in `plan-task`'s Phase 3 hung off *"before handing the table over"*, so a row the orchestrator **authored** mid-run — a Phase-2 scope change, or the full-proposal shortcut where the designer never runs — reached none of them. A new Phase-3 paragraph binds them regardless of authorship, splitting a **statically measurable** claim (executed before the row is pledged) from one needing **pre-change tree state** (marked owed, with a named owner and time); no marker token was minted, since an owed baseline is discharged before the pledge and no grader ever sees it. The full-proposal shortcut gains an eleventh bullet requiring each authored row's **verification method** be checked against the convention doc governing the artifact under change — neither the artifact check (which reads a file) nor the measured-claim check (which re-runs a figure) reaches a claim about *how* something will be verified. `## Execution` gains three rules: a task that **authors its own verification tool** cannot be graded solely by it (the tell is a reported count that does not match the corpus the row names); a later task can falsify a **pledged row**, not just a comment, and the remedy is re-scoping the row rather than relaxing it or deleting the citation; and a **defective** pledge is amended in the open, with the protected requirement verified independently of the row's literal, the amendment recorded in the durable artifact and surfaced to the grading gate, and *defective* distinguished from *decayed* and from *unmet*. `approval-and-audit.md` gains a sixteenth self-audit item catching a **reconstructed** Test Criteria table, which the existing provenance-adjacent items could not — they govern a row's truth, not where it came from. References `ADR-0044` (amending ADR-0017: pre-commitment means the target cannot move *silently*, not that it cannot move) and `ADR-0046`. Behavioral skill/agent change → version bump at release.

- **`designer.md`'s expected-value checks gain three limiting cases and two new rules, and the criteria table is now screened against the change's own planned prose (#328, #340, #367, #370, #371, #391).** The satisfiable-alongside tell now names **positional anchors** — an absolute line number, an `NR`-scoped range — alongside the total-occurrence count and the repo-wide zero, because a positional anchor fails *silently*: the row still evaluates, against the wrong line, and its remedy is a re-derived content anchor rather than a floor. The pinned-total rule's floor now carries to the **byte-exact-sentence** form, since a `grep -c` on a sentence is still a count and citing an individual site is exactly what moves it. The narrower-corpus baseline rule gains its mirror: a row *graded* over a corpus **wider** than it asserts over passes without establishing anything, failing in the safe-looking direction where a world in which the work landed is indistinguishable from one where it did not. A new lead covers **reduction rows** — `N → 0` or `N → M` is only a criterion once every matched occurrence is one the change is supposed to remove, so run the pattern with `-n` and read every hit, then scope it or pair it with an explicit survival assertion. And group 5 gains a second whole-table check: every span the table pins is screened against the prose the same change plans to write, including grep-*support* clauses on manual rows that a banned-literals list would never contain, with a cite-don't-restate instruction treated as a **predictor** of collision rather than a defence against one. `planner.md` carries the mirror for a collision introduced by its own premise correction. References `ADR-0042` and `ADR-0045`, the latter discharging a directive ADR-0038 left for a future criteria-coherence change. Behavioral skill/agent change → version bump at release.

- **`validator` and `code-reviewer` gain a third `unverifiable-as-written` case, a measured-value requirement, a commanded denominator, and a check on their own suggestions (#325, #342, #352, #267, #371).** A row whose expected value is an **empty collection with no mutation record** is now named unverifiable rather than graded, in both graders, each citing `designer.md`'s authoring-side rule rather than restating its remedy. Each grader now reports the **measured** value beside the expected one, and a contradicting measurement forces `not satisfied` — stated separately in both files rather than once-and-cited, because `grep -i measured` over `validator.md` returned zero hits, so there was no owner to cite. The denominator is now derived by a **command over the fetched body** matching both checkbox states, reconciled explicitly against the existing prohibition on counting literal `- [ ]` syntax (that prohibition binds the agent's own instructions; the command binds the fetched issue body — different corpora). Both graders now require the resolved corpus to **match the scope the row asserts over**, reporting a wider-corpus grade as not establishing the row. And `code-reviewer` now checks its **own findings** against the checklist it just graded: a suggestion that would flip a graded row surfaces as an explicit conflict rather than a bare suggestion — the failure being fixed is the silence, not the suggestion. The two graders' deliberately-different corpus defaults are unchanged, per ADR-0035 decision (2). References `ADR-0043`. Behavioral skill/agent change → version bump at release.

- **The named-subject verification rule now covers governing documents, across all five sites that state it (#359).** A claim invoking an ADR, a documented convention, or a `CLAUDE.md` rule by name is a claim *about that rule*, so the rule itself is read — a repo's own summary of it is not a substitute, since a misapplied rule propagates from wherever it was summarized. Widened at `designer.md` step 9 (the owner) plus tailored copies in `planner.md`, `analyst.md`, `plan-task/SKILL.md` and `approval-and-audit.md`, per the repo's cite-and-repeat convention. `analyst.md` carried a **variant** enumeration (`module` rather than `tool`) which is preserved, not harmonized — a find-and-replace would have missed that site entirely. Note the exact span `a function, tool, handler, command, or flag` no longer appears anywhere: widening a list necessarily breaks its exact span, so a search keyed on that string now finds nothing. Behavioral skill/agent change → version bump at release.

## [4.19.0] - 2026-08-20

### Changed

- **`audit-conventions`'s `paths` convention-file overrides are now actually consumed, its hygiene scanners derive their docs-tier walk root from them, and `scanRetiredTokens` widens to `<wikiDir>/` (#383, #384, #366, #386).** `CONVENTIONS.md:82` has documented a `.gvt-agent.json` `paths` override for some time, but nothing read it — a consumer could set the documented example verbatim and it silently did nothing. A new `lib/path-overrides.mjs` resolver fixes that on both sides: validate mode's `evaluateFile`/`evaluateConfig` resolve every declared expectation path through it, and `--fix`'s stale-config TOC scaffold now resolves its target the same way, so the two modes agree on where `docs/TOC.md` actually lives; a `paths` key matching no declared expectation, or an unusable override value, is now reported as a `warning` finding instead of silently ignored. All three hygiene scanners plus the stale-config `--fix` follow-up report (`staleFollowup()`) now derive their walk root from a `paths['docs/TOC.md']` override rather than a literal `'docs'`, so a repo that relocated its knowledge base gets scanned rather than silently reporting "clean" over an empty walk — a new `### Summary` line now names the scanned root and file count so "scanned and clean" is distinguishable from "scanned nothing." Separately, `scanRetiredTokens` — and only `scanRetiredTokens` — now also walks `<wikiDir>/`: `maintain-wiki`'s `lint` verb already owns dead-wiki-links and orphaned pages there, but has no retired-token check of its own, so token drift on the wiki tier was genuinely unowned. `<rawDir>/` stays excluded at both the default repo-root and a nested layout. A `hygiene-probe.mjs` dev tool (not wired into `audit.mjs` or `commands.validate`) ships alongside, for pricing future scanner-scope changes against a real repo before they ship. Reference `ADR-0041`, which amends ADR-0015 decision 1's `wiki/` limb only (leaving its `raw/` limb and decision 2 unamended) and corrects ADR-0022's now-stale walk-boundary claim. Behavioral skill/agent change → version bump at release.

## [4.18.0] - 2026-08-19

### Changed

- **`designer` and `planner` no longer prescribe working-tree git commands as verification mechanisms, and the `[point-in-time]` worked example is replaced by a commit-anchored property (#317, #332, #328).** `plan-task` commits one task at a time, so under the staged-but-uncommitted protocol the worktree is clean by construction — a bare `git diff` reads an empty corpus every time, whatever the change's shape, which is *a check that cannot fail*. Both authoring-side agents shipped that form: `designer.md`'s diff-based-control bullet and `planner.md`'s removals question. Worse, `designer.md`'s `[point-in-time]` **worked example** prescribed a stash-and-pop capture, so a designer following the shipped example produced a vacuous criterion. Both now name the real corpora (`--staged` while the task's work is staged, `<base>...HEAD` once committed), and the structural emptiness of a bare form is distinguished from the *contingent* emptiness #270 already covers — **by citation** of `plan-task`'s Execution section rather than a third phrasing of the same rule. The capture mechanism moved from the *marking* bullet to the *corpus* bullet, which is the category error that let the broken mechanism sit unaudited for four releases: a mechanism parked in a bullet about **when** a row may be graded reads as incidental colour. It is now stated as **properties the mechanism must achieve** — reconstruct every path the capture reads including branch-added ones, leave the index and worktree untouched, anchor the "before" to a commit — with one demonstrated form marked explicitly as *an example, not the required command*, because a command written into guidance is what gets copied and becomes the next stale recipe. The issue's own proposed replacement was **measured and rejected**: a pathspec restore leaves branch-added files on disk, producing a 0-line diff on a component-additive change, and the `git clean` remedy it suggested cannot remove them (they are tracked) while it *does* delete the capture files — either would have shipped a second and third vacuous mechanism. The pathspec caveat is therefore worded **conditionally**, since against `#227` the same form happened to produce a correct capture; the blanket claim is refutable by the tree. Consequently the repaired example **takes no `[point-in-time]` marker at all**: the marker was correct only while the "before" was consumed by restoring it, and a commit anchor survives the branch — repairing a vacuous mechanism invalidated the marking that the vacuous mechanism justified. `planner.md`'s deliverable-collision question also absorbs #328's line-anchor ask, folded in because that line was being rewritten anyway; #328 remains open for its primary content. Reference `ADR-0040`. Behavioral skill/agent change → version bump at release.

## [4.17.0] - 2026-08-18

### Changed

- **`plan-task`'s prescribed-mechanism check becomes a three-question gate, reaches every ticket type, and now distinguishes plan approval from execution approval at four boundary sites (#198, #248, #350).** The mechanism check previously asked only whether a prescribed mechanism was **current** — superseded by shipped code — which #248 and #198 each found insufficient in a different way a passing "is it current?" doesn't catch: a mechanism can be live, un-superseded, and still structurally unable to satisfy the issue's own acceptance criteria (**Is it sufficient?**, #248); and a full proposal prescribes *a* mechanism, not necessarily the best one, with an absent open-questions section being no evidence of a settled design (**Was it ever the best option?**, #198). The three questions are one gate rather than three separate bullets because Q2 and Q3 both fail silently under a passing Q1. The gate was also **ungated from ticket type** — it sat inside the Phase 1 paragraph scoped to "For feature tickets," so it structurally never reached a bug ticket, though #248's own motivating case is a P2 bug; it's now a standalone paragraph reaching both. It further gains reach into a **dependency's behavior and call ordering**, distinct from the version-fact reads (lockfile, installed package version, vendored manifest) the paragraph already directed — types and docstrings state facts, not consequences, and a locally-documented fact about a dependency is not sufficient evidence on its own. The full-proposal shortcut's duplicate mechanism-check clause was **deleted, not sharpened**, so exactly two statements now exist, one per reading path, never three — cross-site drift is how #248 recorded that the gap survived. Separately, **plan approval is now distinguished from execution approval** at four sites: the full-proposal shortcut's combined checkpoint, Phase 3's checkpoint (whose "Ready to proceed?" reads easiest as "shall I implement it?"), the simple-tasks shortcut (which had no checkpoint statement at all), and `approval-and-audit.md`. Plan approval authorizes Phase 4 (save, branch, acceptance-criteria write, prep commit) and stops there; the first implementer dispatch needs its own separate, explicit go — reported after a run read an `AskUserQuestion` about design forks as a go-ahead and executed nine tasks and two commits without one. Reference `ADR-0039`. Behavioral skill/agent change → version bump at release.

## [4.15.0] - 2026-08-16

### Changed

- **`gvt-dev:designer`, `gvt-dev:analyst`, and `plan-task` gain three new general Test-Criteria-authoring rules, each assigned a single canonical owner and cited — never restated — everywhere else it applies (#187, #226, #311, #316, #321).** The `verify-at-implementation` bullet now covers a **counterfactual** figure — a number describing a hypothetical rather than the current tree — as that guard's limiting case: there is no live state to re-derive against, so the only remedy is stating the derivation inline and naming the wrong-population failure mode a reader could otherwise check against (#226). A new item-8 rule states the general remedy for a Test Criteria row the tree cannot yet settle: execute it once during the task that makes the prediction real, observe the result, and revert, routing a false prediction to a finding rather than a silent correction (#316); a companion rule covers that hazard's empty-collection shape — an assertion expecting no results can't distinguish "correctly absent" from "structurally incapable of being non-empty" — requiring a mutation that names and constructs the forbidden state, with a mandatory fallback to a direct structural assertion when no such state exists (#311). A new designer step 9, "Verify what you name before emitting," requires every repo-relative path and every claim about a named subject (function, tool, handler, command, flag) be verified — `Glob`'d or marked `(new)`, and read in full rather than pattern-matched or inferred from a nearby signal — grounded in development principle #12; `analyst.md` mirrors it for its own output. #321 cites the same rule at three further sites rather than restating it — the analyst mirror, `plan-task`'s Phase-3 premise cross-check, and `approval-and-audit.md`'s premise self-audit item — each widened to reach a behavioural claim alongside the existing value-based ones; the Phase-3 cross-check's known-red baseline block also gains a note on its own blind spot, that a check green from the start never enters the recorded expected-red set and so sits structurally outside the block's reach. Reference `ADR-0036`. Behavioral skill/agent change → version bump at release.
- **`designer.md`'s Test Criteria cluster is regrouped into five named question-groups, firing ADR-0033's deferred restructure tripwire, and gains a cross-row rule that two rows can each be individually satisfiable and jointly unsatisfiable; `planner.md` mirrors the new structure with two receiving-side checks (#305, #311).** The cluster now reads as five italic group labels — *Is the pattern right?*, *Is the expected value right?*, *Can it be evaluated, and when?*, *Can it be settled by reading at all — or must it be executed?*, and *Do the rows cohere as a set?* — inserted between the existing bolded leads, every one of which is left byte-identical. `planner.md` item 12 gains a set-coherence check (a premise correction the planner makes during transcription can introduce a cross-row conflict the design's authoring-time read could not have seen, since the correction didn't exist yet, so the assembled set is re-read after corrections) and a mutation-backing check (a row pledging the empty-collection mutation above needs a task in the plan that actually performs it — the designer has no task list to confirm this against). Reference `ADR-0037`. Behavioral skill/agent change → version bump at release.

## [4.14.0] - 2026-08-15

### Fixed

- **`plan-task`, `gvt-dev:validator` and `gvt-dev:code-reviewer` correct one defect shape at three layers — a prescribed read of the git index that the staged-but-uncommitted protocol makes vacuous (#306, #312).** `plan-task`'s co-dispatched-criteria prescription recommended a bare `git diff` on paths a co-dispatched task must not touch; under the protocol the implementer has already staged, so the command returns nothing and the check passes unconditionally regardless of what was actually touched — a check that cannot fail. It's corrected to `git diff --staged`, with `--staged` named load-bearing and the protocol named as the cause so a future edit cannot "simplify" it back, and the Execution section now states the general form once: an orchestrator's verification command must read the **index**, not the worktree, and a "nothing wrong" from an empty corpus is not a pass — carrying the tell that `git diff --staged --numstat <path>` printing nothing means *not staged*, not *unchanged* (#306). On the grading side, `code-reviewer.md` and `validator.md` were told to grade acceptance criteria against "the staged diff" with no hedge, while each file's own earlier process step already hedged correctly; for `code-reviewer` the default was simply wrong, since its dispatch is unconditionally post-commit, so the corpus is empty and a full sheet of `satisfied` verdicts renders identically to a real grade. Both agents now resolve the corpus before grading, honour an explicit dispatch comparison over their default, state which comparison they used, and report an empty corpus rather than grading it — and the text states that the two graders' defaults **deliberately differ** (`validator` runs per-task pre-commit, where staged is correct; `code-reviewer` runs post-commit, where staged is empty), so the two are not later harmonized into one rule that reintroduces the bug (#312). **The root cause, also fixed:** `plan-task`'s end-of-run `code-reviewer` dispatch named no corpus at all; it now points the dispatch at the branch diff against the base rather than leaving the comparison to the agent's default, closing the gap #312 identifies at its source. This item was in neither issue's filed criteria — it was scoped in at the design checkpoint because #312's proposed direction called for it and the site lives in the file #306 already edits. Behavioral skill/agent change → version bump at release.

## [4.13.0] - 2026-08-15

### Changed

- **`gvt-dev:designer`, `gvt-dev:planner`, `gvt-dev:validator` and `gvt-dev:code-reviewer` gain a matched pair of guardrails so a criterion or a grade cannot assert more than was actually established, resolved onto two orthogonal axes — timing (when is a row checkable) and outcome (what could the grader establish) (#237, #241, #268, #280, #292, #310).** `designer.md` item 8 already governed whether a criterion could fail, pass, or be evaluated, but said nothing about *when* checking it is legitimate: a row asserting a transition becomes permanently unverifiable after merge, and a row naming an action outside the branch grades as a false failure at review time. A sixth bolded-lead bullet adds two hyphenated inline markers — `[point-in-time]` and `[not-yet-due]` — carried in the row's own text rather than a fourth table column, because the planner transcribes each row into a flat one-line checklist item with no column structure, so a column would be dropped at exactly the transcription boundary the marking has to survive; hyphenation keeps no emphasis or rewrap able to split them (#237). `planner.md` item 12 gains the receiving-side counterpart: only the planner holds the task list the designer never had, so it checks a marked row against that list and records a mismatch under `## Premise corrections` as **defective**, not decayed — a `[point-in-time]` row whose transition no task performs is unverifiable on arrival, and a `[not-yet-due]` row whose action a task does perform scopes out a row that was genuinely due, producing a false pass (#237). On the grading side, `validator.md` and `code-reviewer.md` both gain a fetched-section **denominator** — established from the fetched section itself, never by counting `- [ ]` syntax, since `code-reviewer.md`'s own body carries 20 unrelated checklist rows that would make the naive phrasing ambiguous inside the file carrying it — plus two non-binary verdicts beside the ordinary pass/fail: **`unverifiable-as-written`**, a defect in the criterion's own text (a control-less zero-hit condition, or a point-in-time row whose moment has passed) that files a 🟡 Warning naming the defect, and **out of scope**, a `[not-yet-due]` row reported rather than omitted and never counted unmet, filing nothing at any severity (#241, #268, #292, #310). `code-reviewer.md` gains a fifth Output Format section, placed **first**, before Critical: the checklist is the pledged target and everything below it is discretionary review, with every fetched row appearing exactly once so the denominator arithmetic holds. It also gains two further guardrails governing free-form review claims rather than row verdicts — guardrail 6 requires opening a cited reference rather than recalling it (#280), guardrail 7 requires naming the evidence behind a positive credit, since a wrong "already verified" removes the prompt to look where a wrong finding is merely pushed back on (#268). `plan-task`'s Execution step 3 scopes both grader dispatches to the new markers — a not-yet-due row is reported, never graded unmet and never omitted, at branch review, and a point-in-time row is checked at the gate where its moment falls; step 5 adds the closing-summary requirement (rows pledged and graded, verified, unverifiable-as-written, and out of scope and still owed after merge) and all three components (`plan-task`, `validator.md`, `code-reviewer.md`) now declare `bugTracker.readOne` as `required: false`, closing a pre-existing gap where the fetch was instructed but never declared (#310). **The commit gate stays binary**: neither new state flips `Overall: PASS / FAIL`, so `plugin/CONVENTIONS.md` needed no amendment. Rejected: making `unverifiable-as-written` a hard fail (blocks every commit for the exact population #241 exists for — pre-#218 checklists and consuming repos on a lagging cache — and per ADR-0017 the orchestrator cannot rewrite a pre-committed pledge), and a fail-by-default-with-override (a policy surface the plugin has no precedent for, for a verdict with no durable recording home). ADR-0033's item-8 restructure tripwire was evaluated and deliberately not fired for the designer bullet — it extends the existing chain rather than opening a parallel one, with **#305** named as the correct future trigger. Measured: the audit's optional tally moved 69 of 81 → 72 of 84, and `required` stayed 35 of 35, so the aggregated contract did not widen. Reference `ADR-0034`. Behavioral skill/agent change → version bump at release.

## [4.12.0] - 2026-08-13

### Changed

- **`gvt-dev:designer` and `gvt-dev:planner` gain three new test-criteria-authoring guardrails, chained by back-reference in the order a row must survive them — can it fail, can it pass, can it be evaluated (#259, #270, #272, #298).** `designer.md` item 8 already governed a criterion's *pattern* — the over-broad-grep and unfalsifiable-zero-hit pair — but said nothing about its *expected value* or its *evaluability*, so a row could carry a flawless positive control and still be worthless. Three new bullets close that gap. The first states the complement of the positive-control rule rather than a restatement of it — that rule proves the pattern can match, this one proves the criterion can fail — by requiring a count criterion to carry the baseline it **measured**, obtained by running the row's own command against the pre-change tree and never asserted from reading, with the pass condition strictly beyond it (#259). The second requires a criterion's expected value to remain satisfiable alongside the change's own deliverable, since a rationale sentence, a cross-reference, or a decision record naming what it retires can itself move a pinned count or break a zero; it gives two remedies by criterion shape — a zero over a corpus (enumerate via the tree-wide *discovery* grep, scope the *criterion* to that enumerated set, carve out historical prose) and a pinned total (assert a **floor** over the measured baseline, not the total) (#272, #298). The third states that a positive control evaluated against the *diff* rather than the corpus can be unevaluable at grading time, and unevaluable reads exactly like a pass, with a purely additive change as the common trigger (#270). `planner.md` item 12 gains the receiving-side counterparts, cut by planner capability rather than mirrored one-per-designer-bullet: the baseline is the planner's to **execute**, not read — a vacuous row (one whose baseline already satisfies the pass condition) is recorded under `## Premise corrections` as *defective*, not decayed; ## [3.1.0] - 2026-06-12

### Added

- **`audit-conventions`: `--apply` reconciles against the previewed `--fix` plan
  (#74).** The dry-run now persists its plan (to the OS temp dir, keyed by repo —
  nothing is written to your repo) and `--apply` diffs the freshly-recomputed plan
  against it, printing a reconciliation line — e.g. `Applied 53 of 54 previewed
actions — 1 previewed action no longer applies (re-run --fix to see the current

  previewed action that no longer applied (because the working tree changed between
  the two turns) dropped silently, visible only as an unexplained count change —
  the #70 mechanism. Defense-in-depth guard; it warns and proceeds, never blocks.
  Consumer-visible output change → version bump.

- **`reconcile-mcp-pin`: new maintainer skill — reconcile agent tool inventories
  after an MCP server pin bump (#68).** A plugin that pins MCP servers in
  `plugin.json` `mcpServers` and ships agents enumerating those servers' tools by
  hand must reconcile the inventories every bump — for an agent with a hard
  `tools:` allow-list a missed read tool becomes _uncallable_, a functional
  regression. The skill generalizes genvid-c3's proven
  `tool-surface-reconciliation` runbook: pull the authoritative surface from the
  pinned package (`npm pack` + `registerTool` grep with a count sanity-check), diff

  the release and hands off to `release-plugin`. A new invocable skill is
  consumer-visible surface → version bump. Contract unchanged: declares only `paths.plugin_root`
  (`required: false`) and the `npm`/`git` tools, so the audit's aggregate
  expectations don't widen — genvid-dev, which bundles no MCP servers, is unaffected.

  template shipped `Date: YYYY-MM-DD` with no meaning attached, and the
  authoring step didn't mention the field — so a record (especially a
  _retroactive_ one) could get a date that predated the decision, caught only in
  review. `tech-writer`'s ADR fill step and the template's guidance comment now
  define **Date** as when the decision was _accepted/finalized_ (not when the
  record was written), with explicit handling for retroactive and diffuse
  decisions. Surfaced dogfooding the `docs/decisions/` convention in this repo.
  No contract change.

- **`designer`: validate filter/classify/dedup heuristics against real data (#64).**
  A design could propose a set-partitioning heuristic (allowlist/noise filter,
  dedup key, "skip if X" rule, auto-suppression) that reads as obviously-sufficient
  but matches nothing against the real corpus — the gap then surfaces mid-execution
  (the burbank-playfab case: a "pure-placeholder" suppressor auto-cleared 0 of 664
  localization gaps because every string had a leading word). The designer's friction
  audit (step 4) now carries a **Heuristic-vs-real-data validation** sub-bullet: run
  or hand-trace the rule over a representative real sample and report the actual
  reduction before recommending it, or flag the assumption as unvalidated when the
  corpus can't be cheaply sampled. The empirical analogue of the existing structural
  friction checks (recipe-vs-override, validation-pipeline duality, paired-array
  ordering). No contract change.

  A design that generalizes a proven procedure (runbook, manual recipe, one-off
  script) into parameterized form can read as obviously-correct while a mechanical
  step silently breaks under the parameter ranges the generalization newly admits —
  the original's _fixed_ inputs masked it. Surfaced authoring `reconcile-mcp-pin`:
  the genvid-c3 runbook `npm pack`ed two _different_ packages into a shared dir, but
  the generalized "old vs new of the _same_ package" case made both tarballs unpack
  to `package/` and clobber (caught by the code-reviewer gate, not the design). The
  designer's friction audit (step 4) now carries a **Generalize-a-runbook
  re-derivation** sub-bullet: walk the concrete steps with the boundary values the
  generalization opens up (same-name inputs, N=0/1, duplicates, collisions) and flag
  any the original's constants protected. No contract change.

- **`audit-conventions`: warn on `repo.host` drift vs the git remote (#54).** A
  stale `.genvid-agent.json` `repo.host` (e.g. `bitbucket` after a repo moved to
  GitHub) silently misleads host-specific skills (`create-pr`, `release-*`) at
  the start of a session. Validate mode now infers the host from the `origin`
  remote (`github.com` / `bitbucket.org`, https + ssh forms) and emits a new
  non-fatal **Warnings** section on mismatch, naming the value to set. An absent
  `repo.host` or an unresolvable/unrecognized remote stays silent, and warnings
  never affect the exit code or the required-expectations tally. Warn-only — no
  `--fix` auto-correct.

  bug-symptom-observable gate but no feature equivalent, so a long-lived "feat:"
  tracking issue whose core work already shipped could be routed straight into
  planning — risking re-implementing shipped code. Phase 1 now carries a symmetric
  feature gate (grep for the named capability, read the issue _body_ not just its
  title/labels, scope to open checkboxes or propose closing), and the "issue is
  already a full proposal" shortcut warns that it assumes _unbuilt_ work. Pairs

  and compromise rationale now lands in a committed **decision record**
